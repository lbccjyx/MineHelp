## 2026-09-23 ｜ "出钩中"门槛太紧，**把开火机会吃掉了**（整局不出钩）

- **症状**：用户花了一整局勾一个钱袋子，程序一直不出钩。
- **证据**（trace 状态统计，58 帧）：
  ```
  dep=1:  23 帧   ← 超过 1/3 的帧认为"钩子射出去了"
  worth=1: 58 帧  ← 目标识别一直正常 ✓
  setl=0:  58 帧  ← 静默期没捣乱 ✓
  inObj=1:  9 帧  ← 钩子确实 9 次扫进目标
  near=1:   3 帧  ← 有 3 帧进了开火窗口
  [fire]:   1 次  ← 却只开了 1 枪
  ```
- **机制**：开火条件是 `ready = ... && !HookDeployed && ...`。
  **钩子扫进目标、进了窗口，但那一帧 `dep=1` → 被挡掉。**
- **门槛为什么那么紧**：
  ```
  出钩锁定门槛 = RestR × 1.45 = 59.5px
  实测摆动半径  = 40 ~ 46px
  ```
  **只差 13 像素**。跟踪质心多捞进几像素绳子就越过 59.5 → 误判"射出去了" → 之后 6 帧不开火。
  而**真正的出钩会把钩子送到几百像素外** —— 门槛定在 59.5 毫无必要地紧。
- **修法**：门槛 `1.45 → 2.0`（=82px），解除 `1.25 → 1.5`（=61px），
  静默窗武装保持 `DeployPeak > 2.5`（=103px）。
  **阈值链条自洽**：真出钩必然越过 103；摆动噪声到不了 82。
- **教训**：
  > **约束值必须由"被约束量的真实分布"决定，不能凭感觉设。**
  > 我先量出了静止半径（42~45），却**没有把它和出钩门槛放在一起看** ——
  > 一旦放在一起，59.5 对 46 只有 13 像素余量，一眼就知道太紧。
  >
  > **"某一帧被挡掉"和"整局不出钩"之间，差的就是一个概率。**
  > 23/58 的误判率下，任何一次扫过都大概率撞上 `dep=1`。
- **元教训**：这次同样是**日志的统计数字**（`dep=1` 占 23/58）直接定位的，
  而不是靠读代码推理。**把 trace 的布尔字段统计一下，比逐行看有效得多。**

## 2026-09-23 ｜ 跟踪会**永久失明**（68 秒），没有任何恢复路径

- **症状**（用户描述三点，实为同一根因）：
  1. 大金块的虚线端点超出金块
  2. **钩子是歪的**
  3. **虚线一闪一闪**，然后钩子"歪得更离谱"
- **证据**：
  ```
  [miss] no pixels (n=0) box={X=815,Y=99,...} | BaseR=43.5 RestR=40.6 dep=1 haveAngle=0 noHook=246 gone=68.6s
  ```
  **连续 246 帧、68 秒没找到钩子**，而且 `dep=1`（出钩中标志卡住）、`haveAngle=0`。
- **机制**：
  - `HookBox()` 是**以最后预测位置为中心**的固定框；
  - 钩子射出去后跟踪丢失 → `NoHookFrames > 6` 把 `HookDeployed` 置位 → `> 45` 把 `HaveAngle` 清零；
  - **但搜索框仍然盯着那个陈旧位置**，而真钩子已经摆到别处 → `n=0` 永远成立；
  - **没有任何机制能把它拉回来** → 永久失明。
- **为什么表现为"一闪一闪"**：偶尔有一帧恰好成功 → 画出虚线 → 下一帧又失败 → 虚线消失。**闪烁 = 跟踪在成功/失败之间抖动。**
- **修法**：失明超过 **60 帧（约 3 秒）** 时**重置搜索框到静止位置**：
  ```csharp
  Angle = 0; HookR = RestR; HookX = PivotX; HookY = PivotY + HookR;
  HaveAngle = true; HookDeployed = false; NoHookFrames = 0;
  ```
- **教训**：
  > **凡是"进入某个坏状态"的逻辑，都必须同时有"如何离开这个坏状态"。**
  > 这里是典型的**单向状态机**：能进不能出。
  > 而且它不是立刻坏，是**用了 68 秒才被日志抓到** ——
  > 说明**长时间的坏状态比瞬时故障更隐蔽**，因为它看起来像"正常等待"。
- **元教训**：**`[miss]` 诊断加上之后，这个 68 秒的僵死一眼可见。**
  （`noHook=246 gone=68.6s` 这两个数字是决定性的。）
  这再次印证：**诊断字段的价值远超一次修复** —— 修复只解决一个问题，
  而诊断能让你看见所有还没被想到的问题。

## 2026-09-23 ｜ 兜底函数**静默失效**，而日志还在报成功

- **症状**：钩子依然看不到（`BaseR` 仍是 0）。
- **证据**：日志同时出现这两行 —— **自相矛盾**：
  ```
  [cal] skipped (...) - fallback pivot from client size   ← 声称兜底成功
  [miss] no pixels (n=0) box={X=-150,...} | BaseR=0.0     ← 实际什么也没做
  ```
- **真凶**：兜底函数第一行是 `if (Cur == null) return;`，
  而主循环里 **`v.Cur` 是在标定之后才赋值的**：
  ```csharp
  if (!calibrated) { ... Calibrate ... }   // ← 此处 Cur 仍是 null
  Frame f = cap.Grab();
  v.Prev = v.Cur; v.Cur = f;               // ← 之后才设置
  ```
  所以兜底**直接返回、什么都没做**。
- **第二个错误（更严重）**：我把成功消息**无条件打印**了 ——
  **日志声称做了实际没做的事**。
- **修法**：
  1. `ArtPivotFromClient(Frame f)` **显式接收帧**，不再依赖 `Cur`
  2. 返回 `bool`，**只有真的产生了几何才打印成功**，否则打印 `FAILED to establish any geometry`
- **教训**：
  > **失败路径上的日志必须由"实际结果"决定，不能由"我打算做什么"决定。**
  > 无条件打印成功消息等于**在日志里撒谎** ——
  > 而日志是这个项目唯一的证据来源，**撒谎的日志比没有日志危险得多**：
  > 它会让你排除掉唯一正确的那条线索。
- **元教训**：**"依赖某个变量"的函数，要先确认那个变量在该调用点是否已初始化。**
  这是**第五次**在几何初始化路径上出问题，形态始终一样：
  **"某状态下某个值不存在"**。`Cur` 为 null 是同一模式的第五个实例。

## 2026-09-23 ｜ "边缘目标勾不到" —— 追踪的块是一个**环**，不是钩子

- **症状**：钩子在视觉上摆过瞄准线（用户反复确认），但状态栏只报 −38~−42，
  目标在 −67 时**永不开火**。
- **诊断过程（这一轮走了 5 个被证伪的理论）**：
  | 理论 | 结果 |
  |---|---|
  | 弧线上界 `BaseR*1.60` 削窄摆动 | 放宽后**无变化** → 当时被 0.80 质心门限掩盖（见下） |
  | 质心下界 `0.80*BaseR` 误伤 | 拒绝的都是 26~28px 的真垃圾 ✓ 但不是病因 |
  | "平均"把多个物体缝在一起 | 改最大块后 `picked` **确实跟随 `blobs:`** ✓ 但角度仍错 |
  | 近轴绳子压缩角度 | `r` 升到 44 但**角度没变** ✗ |
  | **形状图（最终定位）** | **块是一个 ~50px 的空心环** |
- **决定性证据**（`[shape]` ASCII 图，`box=(934,118)-(987,169)`）：
  ```
  ...............@@..........
  .............####..........
  ..........#########........
  ........###########........
  ......###############......
  .....########...#######....
  ....####...........####.#..
  ...####.............#####..
  ..#####...............####.
  .######.............######.
  ######..............######.
  ###...................#####
  ```
  **空心环 —— 中间是空的。** 块的大小（~50px）**和弧半径（40px）相当**。
- **为什么"外层像素取平均"必然失败**：**环的外层像素分布在四面八方，
  它们的平均值仍然是环心。** 对环来说"最外层方向"和"质心方向"是同一个东西 ✓
- **机制**：追踪器跟的是**一个紧贴转轴的 50px 环形结构**（绞盘/曲柄），
  而真正的钩子只是这个环上的**一小段**。环心几乎不动 → **角度被压平、两端被削掉**。
- **正确修法（尚未实施）**：用**离转轴最远的那一小簇像素的方向**，
  而不是质心、也不是外层平均。对环 + 钩子，最远点就在钩子那一侧。
- **教训**：
  > **"逐元素筛选再求平均"对对称形状会退化成质心。**
  > 我加了"取外层"就以为改变了方向估计 —— 但对一个环，外层是对称的，平均值不变。
  >
  > **而且这是一次设计时就该想到的事**：`r` 从 33 升到 44（外层确实生效了）
  > 而角度一点没变 —— **这个组合本身就说明"外层的平均值 = 质心"**。
  > 我当时看到了这两个数字，却没有从它们的**组合**里读出结论。

| `[cand]` 块统计 | `picked` 冻结（块选择从未执行） |
| **`[shape]` 字符形状** | **块是一个环 —— 质心法根本不可能对** |

## 2026-09-23 ｜ 跟踪噪声伪装成"钩子扫过瞄准线"（**逻辑错误**）

- **症状**：指着钱袋子，钩子却到处勾别的东西。虚线笔直指向钱袋，绳子却在 +30°。
- **真凶**：**跨越判定被跟踪噪声欺骗**。
- **证据**（trace 原样）：
  ```
  [trace] ang=  3.79 ... tOn=2530ms ... hx=981 hy=164    ← 角度冻结 3.9 秒
  [trace] ang=  3.79 ... tOn=3873ms ... hx=981 hy=164
  [trace] ang=-14.96 ... tOn=   0ms ... crossed=1  *** FIRE ***
  [trace] ang=  5.61 ... tOn=   0ms ... crossed=1
  ```
  角度从 **+3.79 直接跳到 −14.96**（18.75°），跨过了瞄准线 −6.26 → 开火。
- **为什么会这样**：那段时间 `hx,hy` 只在 `(966~983, 161~182)` 这个
  **17×21 像素的小方块**里抖动。**17px 横向抖动 ÷ 半径 46 = 20° 的假角度** ——
  跟踪质心的噪声被当成了真实摆动。
- **三个叠加的漏洞**：
  1. **连续性门限是固定 21.8°** —— 这次跳变 18.75°，**擦边通过**。
     对静止的钩子来说这个门限太宽，而它静止时的全部有效运动只有几度。
  2. **门限拒绝时不更新 `prevAngle`** —— 连续拒绝 3 次后跳变被接受，
     而跨越基准还是**冻结前的旧角度**，于是造出一个假跨越。
  3. **跟踪失败分支没有清跨越基准** —— 同样的后果。
- **修法**：
  1. 门限改为**跟随实测格间距**：`max(0.12, GameStep × 1.8)`
     （`GameStep` 由主循环每帧发布给 `Vision`）
  2. 跟踪失败分支加 `havePrevAngle = false`
- **教训**：
  **"看到跨越就开火"这个判据，前提是"角度变化是真实的"。**
  一旦跟踪有噪声，跨越判定会把噪声解释成运动 ——
  而且**它不需要多次，一次假跨越就足够打偏一枪**。
- **通用**：**基于"变化"的判据必须同时校验"变化是否可信"。**
  这里就是：跨越 + 变化量不超过一个格间距。缺了后半句，判据就是脆的。
- **被证伪的怀疑**：一度以为是转轴又偏了（`piv=978,118` 确实与实测 966 不同），
  但 trace 显示 `hx,hy` 到 (978,118) 的距离稳定在 46 —— **弧线是对的**，

## 2026-09-23 ｜ 环形区域不是凸集：质心会掉回转轴里

- **症状**：`[fire]` 的 `r=33`（应为 40~55）；偶发乱飞的钩子。
- **真凶**：`Vision.HookPixels` 只约束了**像素**在弧线上，没约束**质心**。
- **为什么会这样**：**我错误地用了凸性论证** —— "每个像素都在环上，质心当然也在环上"。
  但**环形区域（annulus）不是凸集**：两个分别位于转轴两侧、距转轴 37px 的像素，
  **平均之后正好落回转轴附近**。
- **实测**（活跃日志，`BaseR = 46.7`，像素下限 `0.80×BaseR = 37.36`）：

  ```
  dep=0 共 678 帧
  质心距转轴：min=26.25  p05=31.62  中位=43.42  max=64.40
  低于像素下限的帧数：110 / 678   ← 几何上"不可能"，但没有约束质心
  ```

  而**质心离转轴越近，角度越不稳定** —— 挪几像素就跳几十度。
  这就是 `r=33` 和乱飞的来源。**上一轮我只堵了像素，漏了质心。**
- **修法**：在 `TrackHook` 里对**质心**再做一次同样的弧线检查：
  ```csharp
  if (BaseR > 6) {
      if (len < BaseR * 0.80) { LostFrames++; return false; }
      if (!HookDeployed && len > BaseR * 1.60) { LostFrames++; return false; }
  }
  ```
- **验证**：`[trace]` 的 `hx,hy` 到 `piv` 的距离**全部落在 37~75**，`[fire]` 的 `r=` 不再出现 33。
- **教训**：**"每个元素都满足某条件"推不出"它们的平均值也满足"。**
  只有当约束集是**凸集**时才成立 —— 环、弧、两个分离的区间都不是。
  凡是"先逐元素筛选、再求平均"的地方都要检查这一点。
- **元教训**：对照方报这个 `FAIL` 时，它自己给的辩解（"日志打的是质心、门限管的是像素"）
  **结论对、理由错** —— 它以为不算矛盾，其实那正是矛盾所在。
  我第一反应也是用凸性反驳它。**两边都错，只有数字是对的。**

## 2026-09-23 ｜ 标定拟合仍然会顶掉实测转轴（**残差偏差的真凶**）

- **症状**：精度**时好时坏、换一局就变**；`[fire] diff=` 从不居中；

  | (987,152) | 30.65° | 41.42° | **10.8°** |

  | (983,154) | 26.57° | 35.84° | **9.3°** |

- **被证伪的怀疑**：这一轮之前，同一个坑我在 ±130/±170 收到 ±25 时就以为堵住了，

- **通用教训**：**标定环节的 bug 会伪装成"精度问题"。**
  它的表现是全局性、系统性、且随运行变化 —— 遇到这种特征，
  第一件事是查 `[cal]` 选了什么，而不是调判定参数。

## 2026-09-22 ｜ 过冲必须按"实测值"补，且要防污染

- **背景**：实测钩子**总朝摆动方向飞过头 1~8°**（这是稳定规律，与上面的"延迟不稳定"不矛盾 ——
  过冲是统计倾向，不是固定延迟）。
- **修法**：每次出钩后量 `over = 实际飞行 − 开火角度`，取最近 8 次的
  **中位数绝对值**，开火时乘上实测摆动方向 `lastDir`。
- **关键约束**：`if (Math.Abs(over) < 0.25)`（14°）——
  超过一两格的"过冲"必然是跟踪故障。日志里出现过 `over=-37°`、`+29°`，
  都是跟踪卡死时量到的垃圾值，**正在污染学习结果**。
- **验证**：`[fire] aim=39.87 hook=30.50` 提前 9.4° → `[flight] flew=39.88`，**差 0.01°**。
- **已知残留缺陷**：`over` 若与 `lastDir` **符号相反**，说明是跟踪故障，
  但现在会被取绝对值后当成"正向过冲"学进去。**待修**。

## 2026-09-22 ｜ 面板输入框打不了字 / 改完被刷新回去

- **症状 1**：面板上所有输入框无法输入。
  **真凶**：我为了防止面板抢焦点加了 `WS_EX_NOACTIVATE`，
  而该样式会让窗口内**所有控件收不到键盘输入**。
  **修法**：去掉该样式，靠 `ShowWithoutActivation` 保证启动不抢焦点。

- **症状 2**：输入的值点"应用"后又被改回旧值。
  **真凶**：150ms 刷新定时器与"点按钮导致焦点移走"之间的**竞态**——
  焦点一离开输入框，定时器立刻用旧值覆盖它，随后"应用"读到的是被覆盖后的值。
  **修法**：用户编辑过的框打 `Tag="edited"` 标记，定时器不覆盖；
  "应用"时立即更新显示源，不等后台线程。

- **症状 3**：填了合法但在旧范围外的值（如飘窗 125）被**静默丢弃**。
  **修法**：放宽范围 + 非法值**标红**提示，不再悄悄扔掉。

- **教训**：**跨线程的 UI 刷新是竞态高发区**；
  **"静默失败"比报错更浪费时间** —— 用户会以为设置生效了。
